Target Framework: Spring Boot

Specific Constraints:
- Centralize repetitive exceptions: when multiple validations could throw the same exception with the same message,
  combine all conditions into a single check and throw the exception once.
- WARNING !!! Use @Query with JPQL inside an existing repository,
  especially if a derived query method becomes too long or unreadable (example, existsByIdlivreLivreIdLivreAndDateRetourIsNullAndIdmembreMembreIdMembreNot).
- Strict adherence to **Spring Data JPA** conventions.
- Use **native CRUD methods** and **Spring Data JPA Specifications** for all data access logic.
- For complex queries, use **Specifications** only when repository-derived methods cannot handle the requirement.
- For pagination, always use `Page<T>` and `Pageable`.
- For relationships, use standard JPA mechanisms (fetch types, and `@EntityGraph` if necessary).
- Code may use `Optional<T>`, `List<T>`, or `Page<T>` depending on context.
- **No custom JPQL or SQL queries**, unless justified as an **extreme exception** (see below).
- Business exceptions must be raised using **runtime exceptions** or **custom Spring exceptions**.

Allowed CRUD Methods and Tools (examples, non-exhaustive):
- `findAll(Pageable pageable)`
- `findAll(Specification<T> spec, Pageable pageable)`
- `findById(ID id)`
- `save(S entity)`
- `deleteById(ID id)`
- Use entity getters/setters for navigating relationships.


Extreme Case – Controlled Exceptions
**Custom JPQL or SQL**:
- Allowed **only** when the business rule cannot be implemented efficiently with Specifications or CRUD methods.
- Native SQL is allowed **only** for strong technical reasons (e.g., performance optimization on large datasets).
- For large datasets:
  - Use **pagination (`Pageable`)** or **batch processing** (`batch size`, `stream()`, `scroll()`).
  - Minimize unnecessary joins and limit selected fields.
  - Avoid loading all data into memory at once.
  - Prefer **paginated** or **streamed** approaches to prevent memory overload.
